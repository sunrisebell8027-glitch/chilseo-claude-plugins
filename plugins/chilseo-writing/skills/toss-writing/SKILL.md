# 토스라이팅 + 핵심 철학

웹 앱을 만들 때 세 가지를 함께 적용한다.

1. **핵심 철학**: 코드를 쓰기 전에 앱이 끝까지 지킬 원칙을 한두 문장으로 정한다.
2. **토스라이팅**: 사용자에게 보이는 모든 문구를 토스 UX 라이팅 기준으로 쓴다.
3. **다크패턴 방지**: 사용자가 원하지 않는 행동으로 몰리거나 갇히는 흐름을 만들지 않는다.

철학이 "무엇을 만들지"를 거르고, 라이팅이 "어떻게 말할지"를 정하고, 다크패턴 점검이 "사용자를 존중하는지"를 지킨다. 학생이 쓰는 화면에서는 세 번째가 특히 중요하다. 아이들은 화면이 시키는 대로 누르기 쉽기 때문이다.

화면 흐름과 시각 디자인은 `toss-design` 스킬이 맡는다. 웹 앱을 처음 만들 때는 이 스킬의 1단계(핵심 철학) → toss-design(흐름·화면) → 이 스킬의 2~5단계(문구·다크패턴) 순서로 진행한다.

근거 자료와 주소는 `references/sources.md`에 있다. 규칙이 헷갈리거나 최신 내용을 확인해야 할 때 거기 적힌 공식 원문을 다시 읽는다.

## 1단계: 핵심 철학 정하기

새 앱을 시작하거나 큰 기능을 더할 때, 구현 전에 철학 문장을 먼저 제시한다.

- 형식: "누가, 어떤 상황에서, 무엇을 얼마나 쉽게 하고, 무엇은 절대 하지 않는다."
- 예: "선생님이 수업 중 10초 안에 쓸 수 있고, 학생 정보는 이 기기 밖으로 나가지 않는다."
- 사용자가 이미 철학을 말했거나 프로젝트 CLAUDE.md에 있으면 그것을 그대로 쓴다. 없으면 대화 맥락으로 초안을 만들어 보여 주고 확인받는다.
- 이후 기능을 넣을지 판단할 때마다 이 문장에 비춰 본다. 철학과 어긋나는 기능(예: 위 예시에서 로그인, 서버 저장, 학생 이름을 외부 AI로 전송)은 빼거나, 넣어야 한다면 왜 어긋나는지 사용자에게 알린다.
- 한 화면에서는 한 가지 결정만 하게 한다(One Thing per Screen). 선택지가 많아지면 단계를 나눈다.

## 2단계: 문장 규칙 (앱인토스 공식 UX 라이팅 가이드)

문장 하나하나를 고칠 때 쓰는 규칙이다. 위에서부터 차례로 적용한다.

1. **해요체**: 모든 문구를 해요체로 쓴다. 상황과 맥락을 가리지 않는다. 한 앱 안에서 "합니다"와 "해요"가 섞이면 여러 사람이 말하는 것처럼 들린다.
   - "저장되었습니다" → "저장했어요"
2. **능동형**: 누가 했는지 드러나게 쓴다.
   - "됐어요" → "했어요": "설정됐어요" → "설정했어요"
   - "~된" 빼기: "선택된 학생" → "선택한 학생"
   - 동사 바꿔 쓰기: "알림이 발송돼요" → "알림을 보내요"
3. **긍정형**: "안 돼요", "없어요" 대신 "~하면 할 수 있어요"로 다음 행동을 알려 준다.
   - "학생이 없어서 배정할 수 없어요" → "학생을 2명 이상 넣으면 배정할 수 있어요"
   - 일부 기능만 못 쓸 때 부정문만 쓰면 사용자는 훑어보다가 앱 전체를 못 쓴다고 오해한다. 쓸 수 있는 것을 먼저 말한다.
4. **캐주얼한 경어**: 존중은 하되 과하게 높이지 않는다.
   - "~시" 빼기: "확인하시겠어요?" → "확인할까요?"
   - "계시다" → "있다", "여쭈다" → "확인하다·묻다", "께" → "에게"
   - 빼서 어색하면 알고 싶은 정보를 주어로 다시 쓴다: "학생 명단을 가지고 계시나요?" → "학생 명단이 있나요?"
5. **명사 나열 풀기**: 한자어 명사를 이어 붙이지 않고 동사로 푼다.
   - "명단 등록 완료" → "명단을 등록했어요"
   - 풀기 어려우면 "{명사}가 {명사}해서"로만 풀어도 된다: "용량 초과로 저장 실패" → "용량이 꽉 차서 저장하지 못했어요"

### 예외: 이럴 때는 규칙을 굽힌다

규칙을 기계적으로 적용하면 오히려 뜻이 흐려지는 경우가 있다.

- **수동형이 나을 때**
  - 서비스 종료나 기간 만료처럼 끝나는 대상을 강조할 때: "체험 기간이 끝났어요", "기록은 학기 말에 정리돼요". 단, 수업 타이머처럼 매번 끝나는 기능에는 "종료돼요"를 쓰지 않는다.
  - 사용자의 행동 때문에 생기는 결과를 알려 줄 때: "지우면 모둠 기록도 함께 삭제돼요"
  - 사용자를 안심시킬 때: "학생 정보는 이 기기에만 저장돼요"
- **경어가 나을 때** ("~시나요?", "~셨나요?")
  - 사용자 맥락을 짚어 묻거나 상황을 짐작해 물을 때: "지난 시간 모둠을 다시 쓰시나요?"
  - 설문처럼 사용자의 선의가 필요할 때
- **부정형이 나을 때**
  - 정책상 쓸 수 없을 때. 이유를 함께 쓴다: "학생 화면에서는 명단을 바꿀 수 없어요. 선생님 화면에서 바꿔 주세요."
  - 일부 기능만 못 쓸 때 어떤 기능인지 분명히 알려야 할 때
  - 사용자를 안심시킬 때: "학생 이름은 다른 곳으로 보내지 않아요"
- **"되어요"는 언제나 "돼요"로 쓴다.**

## 3단계: 화면 단위 원칙 (토스 라이팅 원칙 8가지)

문장 규칙이 "문장을 어떻게 쓰나"라면, 이 원칙은 "화면에 무엇을 남기나"를 정한다.

| 원칙 | 하는 일 |
|---|---|
| Predictable hint | 버튼·링크만 보고 다음에 무슨 일이 생길지 알 수 있게 쓴다. "확인" 대신 "모둠 배정하기". |
| Weed cutting | 문장 안에서 빼도 뜻이 같은 단어를 지운다. |
| Remove empty sentences | 화면 안에서 정보 없는 문장을 지운다. "○○ 기능입니다." 같은 소개 문장. |
| Focus on key message | 화면마다 꼭 전할 메시지 하나에 집중한다. |
| Easy to speak | 전문 용어 대신 말하듯 쉽게. "로컬스토리지" → "이 기기". |
| Suggest than force | 겁주거나 강요하지 말고 이득을 제안한다. |
| Universal words | 누구나 이해하고 아무도 불편하지 않은 말을 쓴다. "학부모님" → "보호자". |
| Find hidden emotion | 상황 속 사용자 감정을 헤아린다. 오답에 "틀렸습니다" → "아쉬워요! 한 번 더 해 볼까요?" |

### 버튼과 대화창

- 버튼은 "동작 + 하기"로 쓴다: "저장하기", "다시 섞기", "결과 보기". "확인", "제출", "진행"처럼 뭉뚱그린 말은 동작 이름으로 바꾼다.
- 위에서 이미 설명한 이득을 버튼에 그대로 되풀이하지 않는다. 버튼에는 누르면 일어날 일을 쓴다.
- **대화창의 닫는 버튼은 "닫기"로 쓴다.** "취소"는 하던 작업이 취소된다고 오해할 수 있다. 정말로 진행 중인 작업을 취소하는 버튼만 "취소"라고 쓴다.
- 되돌릴 수 없는 동작은 결과를 그대로 적는다: "명단 지우기" / "그대로 두기".

### 오류 문구

- 무엇이 일어났는지 + 어떻게 하면 되는지를 함께 쓴다. 사용자를 탓하지 않는다.
- "잘못된 입력입니다" → "이름을 한 줄에 한 명씩 넣어 주세요".
- 오류 코드나 기술 메시지(`Error:`, `undefined`)를 화면에 그대로 보여 주지 않는다.

상황별 예시는 `references/examples.md`를 본다. 문구가 많은 화면을 만들거나 기존 문구를 일괄 점검할 때 읽는다.

## 4단계: 다크패턴 막기 (앱인토스 다크패턴 방지 정책)

토스는 아래 다섯 가지를 출시할 수 없는 사용성 오류로 본다. 교실 앱에서도 같은 이유로 피한다. 사용자가 예측할 수 없거나 거절할 수 없는 흐름은 신뢰를 잃게 한다.

1. **들어오자마자 화면을 가리는 팝업**: 앱을 열면 바로 쓰려던 화면이 나와야 한다. 안내, 알림 동의, 공지는 필요한 순간에 화면 안에서 보여 준다.
2. **뒤로 가기를 막는 팝업**: 나가려는 사용자를 붙잡는 창을 띄우지 않는다. 작업 내용이 사라질 수 있다면 자동 저장하고, 그 사실을 짧게 알린다.
3. **나갈 길이 없는 화면**: 꼭 하지 않아도 되는 행동이라면 "닫기", "나중에 하기", "건너뛰기"를 눈에 띄게 둔다. 거절 버튼을 흐리게 하거나 숨기지 않는다.
4. **예상하지 못한 순간의 전면 화면**: 버튼을 눌렀는데 기대와 다른 화면(광고, 다른 기능 홍보)이 뜨지 않게 한다.
5. **결과를 예상할 수 없는 버튼**: 버튼만 보고 다음 행동을 알 수 있어야 한다. 버튼 위에 과장되거나 중복된 설명을 붙이지 않는다.

학생 화면에서는 여기에 더해 다음을 지킨다.
- 순위, 경쟁, 시간 압박을 꼭 필요할 때만 쓴다.
- 애원하거나 겁주는 문구, 우는 캐릭터 같은 감정 호소를 쓰지 않는다.
- 학생 정보를 입력받기 전에 무엇을 왜 받는지, 어디에 저장하는지 먼저 알린다.

## 5단계: 마무리 점검

코드를 다 쓴 뒤 두 가지를 한다.

**① 자동 검사**: 문구 검사 스크립트를 돌린다.

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/check_copy.py" <파일이나 폴더>
```

`${CLAUDE_SKILL_DIR}`는 이 스킬 폴더다. 값이 채워지지 않는 환경(Claude 앱 등)에서는 이 스킬 폴더 안의 `scripts/check_copy.py`를 찾아 실행한다.

HTML·JS·JSX·TS·TSX·Vue·Svelte 파일에서 한글 문구만 골라 "합니다", "되어요", "취소", "~시겠어요", 명사 나열, 뭉뚱그린 버튼 이름 같은 표현을 찾아 준다. 결과는 **확인할 후보**다. 위의 예외에 해당하면 그대로 두고, 아니면 고친다.

**② 눈으로 확인**: 아래를 훑어본다. 고친 문구가 있으면 사용자에게 짧게 알린다.

- 해요체로 통일했는가? "되어요"가 남아 있지 않은가?
- 버튼만 보고 결과를 예측할 수 있는가? 대화창 닫기 버튼이 "닫기"인가?
- 지워도 되는 단어·문장이 남아 있지 않은가?
- 겁주는 표현, 전문 용어, 특정 집단을 소외시키는 단어가 없는가?
- 들어오자마자 뜨는 팝업, 나갈 수 없는 화면이 없는가?
- 기능 목록이 1단계 철학과 어긋나지 않는가?

## 범위

- 코드 주석, 변수명, 커밋 메시지, 개발 문서에는 적용하지 않는다. 사용자에게 보이는 화면 문구만 해당한다.
- 사용자가 다른 말투(예: 반말, 영어 UI, 공문서체)를 명시하면 그 요청을 따르고, 나머지 원칙(간결함, 예측 가능한 버튼, 다크패턴 방지)만 적용한다.
- 법령 문구나 약관처럼 바꾸면 안 되는 글은 원문을 두고, 옆에 쉬운 설명을 덧붙인다.
- 토스의 문구를 "토스 공식 문구"라고 소개하지 않는다. 이 스킬은 공개된 원칙을 참고해 만든 비공식 가이드다.
